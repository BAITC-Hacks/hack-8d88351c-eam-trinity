ЧТО ДОЛЖНО ПОЛУЧИТЬСЯ

CITYPROOF — визуальная лаборатория, где пользователь выбирает
пять городских мероприятий, а ИИ-агент проверяет последствия
в обычных условиях и при одном учебном зимнем событии.

Основной опыт:
1. Открывается красивый рабочий экран с объёмной схемой пяти районов.
2. Пользователь выбирает мероприятия и районы в пределах бюджета.
3. Нажимает «Проверить план» или задаёт вопрос агенту.
4. Агент реально вызывает инструменты расчёта и стресс-теста.
5. Сцена и показатели обновляются, появляются проверяемые объяснения.
6. Нажатие «Откуда число?» открывает соответствующий расчёт
   и выделяет нужный район. Можно задать дополнительный вопрос.

Это не лендинг, не статический макет и не чат с заготовленными ответами.
Главная функция — настоящий агент, связанный с работающим симулятором.

СТЕК И ОРГАНИЗАЦИЯ

Сначала осмотри существующий репозиторий и состояние Git.
Если приложение не начато: Next.js App Router, TypeScript, React,
Tailwind CSS, серверные Route Handlers, официальный OpenAI SDK.
Фронтенд и бэкенд находятся в одном проекте.
Если рабочий стек уже есть, не переписывай всё без необходимости.

Не нужны мобильное приложение, отдельный Python-бэкенд, база данных,
регистрация, платежи или обучение собственной нейросети.
Используй один package manager и совместимые версии зависимостей.

ДИЗАЙН — ЧАСТЬ ОСНОВНОГО ЗАДАНИЯ

Создай цельный премиальный интерфейс: тёмный графит, сдержанный
бирюзовый акцент, качественная типографика с кириллицей,
воздух, крупные показатели, аккуратные границы и плавные переходы.
Не делай шаблонную стену одинаковых карточек и кислотного свечения.

Сверху — CITYPROOF, бюджет, количество решений, «Учебная модель».
Слева — каталог мероприятий и выбор района.
В центре — большая интерактивная изометрическая SVG-сцена города.
Справа — панель агента, запросы, журнал инструментов и объяснения.

Сцена содержит пять подписанных районов, условные объёмные здания,
дороги и зелёные участки. Это схема, не точная география Астаны.
Не подключай тяжёлую 3D-карту, WebGL или платный картографический API.

Выбор района раскрывает показатели. Подсветка связана с реальными
результатами движка. Видны режимы исходное/после решений/событие.
Не используй декоративные изменения вместо вычислений.

Все кнопки работают. Проработай загрузку, ошибки, отсутствие API,
отмену анализа и устаревший ответ. Проверь читаемость на ноутбуке.

НАСТОЯЩИЙ ИИ-АГЕНТ ОБЯЗАТЕЛЕН В ПЕРВОЙ ВЕРСИИ

Реализуй цикл: запрос пользователя → модель вызывает инструмент →
сервер выполняет функцию → результат возвращается модели →
при необходимости следующая проверка → объяснение с доказательствами.

Инструменты: get_model_rules, evaluate_scenario, run_stress_test,
get_evidence. Сравнение двух пользовательских вариантов добавляй
только после работающего основного сценария.

Агент сам выбирает нужные проверки по запросу, но не изменяет
пользовательский набор мероприятий или данные модели.
Для аудита с зимним событием действительно выполняются оба расчёта.
Последующий вопрос должен использовать данные актуального сценария.

Журнал показывает реальные вызовы, статусы и результаты инструментов,
а не выдуманные «размышления». Объяснения ссылаются на существующие
записи расчётов. Числа и дельты берутся из движка, а не из фантазии LLM.
Не выбирай за пользователя городские решения и не объявляй
«глобально лучший план» или гарантированную безопасность города.

Проверь API в начале работы, затем проверь реальный вызов инструмента.
Runtime-модель задаётся через OPENAI_MODEL: используй доступный
по выданному ключу API model ID, не название режима из интерфейса Codex.
Ключ — только на сервере. Не публикуй его в Git, логах или браузере.
При отсутствии ключа сообщи об этом и продолжай разработку,
но не представляй AI-интеграцию завершённой.

ТОЧНОСТЬ И СТРЕСС-ТЕСТ

Все данные, правила бюджета, пяти решений, направлений, районов,
конфликтов, лагов и синергий реализуй по источникам и полному брифу.
Невалидный набор не получает численный итоговый Score.
Официальную формулу не меняй; промежуточные числа не округляй.
Исходное состояние и незавершённый пользовательский план различай.

Зимнее событие берётся только из stress_events.json.
Его параметры видны до запуска и подписаны как допущения команды.
Оно не изменяет официальную модель, не накапливается при повторном
запуске и не даёт отдельным мероприятиям выдуманную защиту.
Официальный результат и эксперимент показывай раздельно.

GITHUB — НЕ ОСТАВЛЯЙ РЕЗУЛЬТАТ ТОЛЬКО ЛОКАЛЬНО

Разрешаю создавать осмысленные коммиты и отправлять изменения
этого проекта в уже подключённый командный репозиторий
штатным способом с соблюдением разрешений среды.

Вначале проверь репозиторий, remote и рабочую ветку.
Не создавай новый репозиторий, не подменяй origin и не удаляй чужой код.

После законченных этапов:
- запускай проверки, обновляй STATUS.md фактическими результатами;
- проверяй diff и отсутствие секретов;
- делай commit относящихся к этапу файлов;
- отправляй рабочую ветку через git push, когда это доступно;
- проверяй, что commit действительно появился в удалённой ветке.

Не применяй force-push, reset --hard и слепой git add .
Не выдумывай авторство или вклад участников.
Не публикуй .env, токены, node_modules и артефакты сборки.

Если среда Codex публикует через PR, используй доступный механизм.
Если нужна ручная кнопка Create PR или Merge, скажи об этом прямо.
Не обходи защиту веток и не сливай PR без просмотра человеком.
Не называй локальный commit или открытый PR обновлённой основной веткой.
При запрете отправки сохрани результат и точно сообщи причину.

ПОРЯДОК РАБОТЫ И ПРОВЕРКИ

Делай короткие законченные этапы:
1. Репозиторий/API, данные, движок, тесты и визуальный каркас.
2. Работающий агент, один стресс-тест и связь с интерфейсом.
3. Завершённая объёмная сцена, взаимодействия и состояния ошибок.
4. Проверки, README, демонстрация и публикация последней версии.

Агент, стресс-тест и сцена обязательны; экспорт и A/B — дополнительные.
Не откладывай AI до конца ради дизайна и не сдавай голый расчётный экран.
Сначала закончи одну цельную цепочку, затем улучшай её.

Проверь ограничения, контрольные данные из JSON, лаги, синергии,
отрицательные эффекты, порог, повторяемость события и реальные tools.
Запусти тесты, typecheck, lint и production build доступными командами.
Открой приложение и проверь пользовательский сценарий в браузере,
если инструмент доступен. Не выдумывай результаты проверок.

README на русском: назначение, реализованные функции, архитектура,
установка, переменные окружения, запуск, сценарий проверки, источники,

В конце сообщи: что работает, что проверено, как запустить,
статус AI, репозиторий, ветку, hash опубликованного commit,
статус PR/объединения и оставшиеся ручные действия.
Напомни отдельно нажать «Сдать решение» на платформе хакатона.

Начинай реализацию после короткого осмотра. Не ограничивайся планом
