## 2. Зафиксированная концепция и объём

Название: CITYPROOF.
Подзаголовок: «Аким на 5 часов · лаборатория городских сценариев».
Основная мысль интерфейса: «Посмотри результат. Измени предположение. Проверь, что изменилось».

Продукт — одно веб-приложение в браузере, не APK, не Telegram-бот, не приложение Flutter. В новой реализации не нужны отдельный Python/Express-бэкенд, микросервисы, база данных, авторизация, платежи, настоящая GIS-карта, LangChain, MCP или отдельные AI-персоны. Не добавляй инфраструктуру без необходимости.

### Обязательная первая версия: один законченный агентный сценарий

1. Сразу открыть рабочее приложение: стилизованная объёмная схема пяти районов, бюджет 100, каталог, панель агента. Не landing page.
2. Дать пользователю выбрать ровно пять разных мероприятий и районы, где нужно.
3. Программно проверить все ограничения и рассчитать официальный результат.
4. Показать изменения, источники чисел и отдельно подписанный результат по заданию.
5. По запросу «Проверь мой план в обычных условиях и при учебной зиме» настоящий ИИ-агент вызывает инструменты расчёта и стресс-теста, получает результаты и при необходимости раскрывает детали через инструмент evidence.
6. Во время выполнения показывать реальные операции, после него — краткое объяснение и ссылки на проверяемые данные.
7. Нажатие на доказательство выделяет соответствующий район/индикатор и раскрывает вычисление. ИИ и сцена работают как части одного продукта.
8. Пользователь может задать дополнительный вопрос: «Почему изменился этот показатель?» Агент получает нужную запись расчёта и отвечает на её основании.

**Полноценный агент, один учебный стресс-тест и объёмная интерактивная сцена входят в обязательную первую версию.** Одного текстового ответа модели поверх готового JSON недостаточно для завершения задания. Допустимы промежуточные технические шаги, но их нельзя выдавать за готовый продукт.

### Только после первой версии

Сохранить пользовательские варианты A/B, сравнить при ОДИНАКОВОМ событии, экспортировать паспорт симуляции в JSON/печатный HTML. Не откладывай основной агентный сценарий ради этих функций.

Из другого предложения НЕ включать в обязательный объём: полный перебор пространства решений, «глобальный оптимум», Human vs AI с победителем, автономный выбор городской политики, автоматическое «исправление» плана, пять кризисов сразу, гарантированный сценарий «всё стало зелёным», сертификат безопасности, генерацию презентации или PDF.

Решения выбирает пользователь. Агент объясняет правила, последствия и различия, не ранжирует политические решения и не выдаёт учебную модель за рекомендацию реальной городской политики. Не маркируй варианты словами «лучший», «безопасный», «одобренный» или «победитель».

Чистые функции не зависят от UI, LLM, времени и сети. Одна реализация движка используется сервером, тестами и при необходимости клиентским preview. Сервер всегда сам валидирует и считает; он не доверяет присланной стоимости, весам, дельтам или результатам.

Семантический контракт:

```ts
type Decision = { measure_id: MeasureId; district_id?: DistrictId };
type ScenarioInput = { decisions: Decision[] };

type ValidationIssue = {
  code: string;
  message: string;
  measure_ids?: MeasureId[];
};

type Evaluation =
  | { valid: false; score: null; errors: ValidationIssue[] }
  | {
      valid: true;
      score: number;
      cost: number;
      remaining_budget: number;
      // baseline/updated indicators, district totals, mean,
      // minimum, critical pairs, effect ledger, evidence IDs,
      // normalized decisions and model version.
    };
```

Это иллюстрация: реализуй полные строгие типы без `any`. Внешний JSON валидируй во время исполнения, например Zod или эквивалентной явной проверкой. Unknown IDs, дополнительные клиентские коэффициенты и неверные scope должны отклоняться. Для city-мер `district_id` отсутствует; если API tools требует nullable-поле, нормализуй `null` в отсутствие до бизнес-валидации. Не принимай выдуманный район `city` как шестой район.

## 4. Официальная валидация и движок

Из `hackalem_model.json`:
- Бюджет 100, ровно пять мероприятий, не более двух в одном направлении.
- Каждое мероприятие только один раз независимо от района.
- District scope требует район; city scope не принимает район, стоит один раз, влияет на пять районов.
- M1 и M3 несовместимы глобально.
- M4/M7 и M5/M13 несовместимы только в одном районе.
- Остаток бюджета не даёт бонуса.
- Невалидный план не имеет результата Score, даже если нарушено только число решений.
- Порядок выбора не влияет на результат.

Алгоритм:
1. После успешной валидации скопировать исходную матрицу индикаторов.
2. Для каждой меры прибавить эффекты с коэффициентом `(8 - lag_quarters) / 8`.
3. Добавить фиксированные синергии в район районной меры: M1/M2 -> T1 +2; M10/M12 -> B1 +2; M5/M6 -> E2 +2. Не уменьшать синергии лагом.
4. Сложить все изменения и только затем один раз clip каждого индикатора до [0,100].
5. Районный результат — взвешенная сумма десяти индикаторов по JSON.
6. Среднее города — взвешенная по долям населения сумма районных результатов.
7. Ncrit — число всех пар район/индикатор со значением СТРОГО <40.
8. Официальная формула: `0.7 * city_mean + 0.3 * minimum_district_value - critical_count`.

Не теряй отрицательный эффект T1 у M11. Не округляй промежуточные значения. Для отображения используй два знака, для тестов — tolerance.

`computeBaseline()` — отдельный служебный расчёт исходного состояния. Он не превращает пустой набор пользовательских решений в валидный сценарий. Для draft <5 показывай бюджет/карточки/подсказки, но не числовой итог сценария.

Журнал по индикатору должен содержать: исходное значение, каждую применённую дельту, коэффициент лага, синергию отдельно, сумму до clip, результат после clip. Возвращай устойчивые evidence IDs.

Не называй разницу результата после удаления меры её однозначным «вкладом»: удаление даёт четыре решения и нарушает правила, а минимум, пороги и синергии нелинейны. В этой версии достаточно точного журнала индикаторов; не реализовывай Shapley или оптимизатор ради объяснимости.

## 5. Стресс-тест: отдельное учебное допущение

Первый и единственный обязательный для отличительной функции event — `winter_demo` из `stress_events.json`.

Он означает не прогноз зимы, а фиксированный технический эксперимент: к каждому району после официального расчёта прибавляются указанные в конфигурации дельты T1 и C1. Пользователь видит коэффициенты ДО запуска. Это наши демонстрационные условия; они не взяты из исходного ТЗ.

Формальная последовательность:
- Сначала `evaluateScenario(plan)` на неизменных данных организатора.
- Если план невалиден — стресс-тест тоже недоступен.
- Создать НОВУЮ матрицу из рассчитанных индикаторов.
- Применить выбранное событие один раз: `J[d,k] = clip(I_after[d,k] + shock[d,k], 0, 100)`.
- Пересчитать показатели той же формальной функцией агрегации, но хранить результат как `experimentalResult`, не заменяя официальный результат.
- Сравнение «без события / с событием» и A/B под одним event_id+version использует одинаковые параметры.

Никакой мутации исходной матрицы, накопления события при повторном клике, переиспользования случайных значений или автоматического изменения модели. Кнопка повторного запуска должна давать тот же результат. Event `none` — тождественное преобразование.

Не добавляй M14, M13 или любому другому мероприятию особую защиту от события: в исходной модели такой зависимости нет. Не уменьшай шок в присутствии определённой меры без отдельной явно описанной модели; в текущей версии такой дополнительной модели НЕ ДЕЛАТЬ.

Честные подписи:
- «Официальный расчёт по данным задания».
- «Учебный стресс-тест: допущения команды».
- «Значений ниже порога модели: …».
- «Результат относится только к выбранным условиям».

Не использовать «город безопасен», «план провалился», «устойчив при любых кризисах», «сертификат безопасности». Отсутствие индикаторов <40 не является доказательством реальной безопасности. Изменение плана B — новый альтернативный сценарий с исходным бюджетом 100, а не бесплатное изменение уже потраченного бюджета через два года.

## 6. Премиальный интерфейс и объёмная модель города

Создай не типовой dashboard из множества несвязанных карточек, а одну цельную рабочую сцену. Язык — русский. Пользователь видит продукт сразу, без длинного приветственного экрана и регистрации.

### Визуальная система
- Фон тёмно-графитовый, например #0B0F14; панели #121923; основной текст #EAF0F5; второстепенный #94A3B8; сдержанный бирюзовый акцент #48D7C5. Это предложенные дизайн-токены, не данные симуляции.
- Ограниченная палитра, деликатные границы/тени, один ритм отступов, единые радиусы. Никаких кислотных градиентов, светящихся рамок вокруг всего или emoji вместо навигации.
- Чёткая типографика с кириллицей, табличные цифры, крупные ключевые значения. Загрузка внешнего шрифта не должна быть обязательна для сборки.
- Короткие переходы 150–300 мс, понятные hover/focus/selected/disabled, поддержка reduced motion. Цвет не единственный носитель смысла.
- Основные проверки на 1440×900 и 1366×768; на более узком экране панели перестраиваются. Подписи и кнопки не обрезаются. Не фиксируй трёхколоночный layout на телефоне.

### Компоновка
Сверху: CITYPROOF, «Краш-тест городских сценариев», бейдж «Учебная модель», бюджет и число решений.
Слева: компактный каталог 14 мероприятий с фильтрами пяти направлений, стоимостью, лагом и областью действия. Район выбирается только для районной меры. Выбранные меры видны и удаляются без потери остальных.
В центре: большая изометрическая модель из пяти районов, режимы «Исходное состояние», «После решений», «Учебное событие», выбор отображаемого индикатора и легенда.
Справа: полноценная панель ИИ-агента с полем запроса, кнопкой «Проверить план», журналом инструментов и последующими вопросами. Панель не прячется в дополнительную страницу.
Результат и детали индикаторов — компактная полоса/нижняя панель. «Откуда число?» раскрывает понятную арифметику, а не огромный сырой JSON.

### Модель города — обязательная интерактивная сцена
- Реализуй лёгкую изометрическую SVG-сцену с пятью различимыми районами: небольшие объёмные здания, дороги, зелёные участки, простые объекты инфраструктуры. Объём достигается гранями, тенями и проекцией; WebGL и полноценная 3D-GIS не нужны.
- Это НЕ точная география Астаны. Подпись «Условная схема пяти районов». Не скачивай границы, спутниковые снимки, 3D-модели или карты с платными ключами.
- Районы выбираются нажатием, имеют горизонтальные читаемые названия; выбранный район связан с карточкой его десяти индикаторов.
- Выбранные районные мероприятия отмечаются маркерами в соответствующем районе; городские меры показываются как общегородские, не дублируют стоимость.
- Подсветка/индикаторные полосы меняются из рассчитанного состояния. Легенда объясняет выбранный индикатор и единицы. Не назначай районам политические рейтинги или произвольные статусы качества.
- При раскрытии evidence подсвети именно подтверждающий район и индикатор. Пользователь должен видеть связь ответа агента со сценой.
- Снег или декоративная анимация не заменяют расчёт события. Не выдумывай изменение трафика, население, новые здания или аварии, которых движок не моделирует.
- До валидных пяти решений сцена показывает исходные данные и маркеры черновика; не изображает черновик как завершённую симуляцию.

### Поведение и честные состояния
Кнопки: «Пример из задания», «Проверить план», «Исходное состояние», «Сбросить», «Остановить анализ». Пример загружается как стартовый набор, не как рекомендуемое или оптимальное решение; все результаты вычисляются заново.

Основная кнопка запускает агентный аудит выбранного плана. Пользователь заранее видит, включён ли учебный зимний сценарий, и его допущения. Дополнительные быстрые запросы: «Объясни изменения», «Покажи расчёт выбранного показателя». Не нужны неработающие декоративные кнопки.

Все числовые карточки получают данные от движка, не из свободного текста LLM. Изменения подписаны в пунктах индекса, не в выдуманных минутах, процентах населения или тенге. Официальный и экспериментальный результаты всегда различимы.

Загрузка, ошибки бюджета/конфликтов/районов, отсутствие API, таймаут, остановка и устаревший анализ должны иметь законченный дизайн. Пока работают инструменты, показывай действительно начатые операции, а не фиктивную историю «размышлений».

Изменение плана или параметров события инвалидирует прежний AI-анализ. Идентификатор снимка сценария должен исключать отображение ответа для старого плана рядом с новыми данными. Для сравнения порядок выбора нормализуется.

Локальное сохранение допустимо с явным восстановлением и сбросом. База данных не нужна. Каждый новый сценарий использует неизменные исходные условия.

## 7. Реальный AI-agent, а не имитация

Различай модель, которой пользователь пользуется в Codex для написания кода, и runtime-модель приложения. Название в интерфейсе Codex не преобразуется автоматически в API model ID. Используй `OPENAI_API_KEY` и `OPENAI_MODEL`, при необходимости разрешённый организатором `OPENAI_BASE_URL`. Не сочиняй идентификатор GPT-6 или наличие API-квоты.

В самом начале сделай минимальный smoke test доступного API и выбранной модели. Отсутствие ключа не блокирует разработку математики/UI, но должно быть явно отмечено как незавершённая AI-интеграция. Не подменять её статической заготовкой с подписью «AI».

Ключ только в серверном окружении, `.env.local` исключён из git, `.env.example` содержит только пустые поля. Не ставить `NEXT_PUBLIC_` перед секретами. Не выводить ключ, заголовок Authorization и полные environment dumps в лог. Ошибки логировать без секретов.

Используй официально поддерживаемый function calling доступной модели. Если доступен прямой OpenAI endpoint, предпочтительна Responses API. Не смешивай её формат с Chat Completions; если организатор выдал другой совместимый endpoint, проверь его контракт и документируй фактическую интеграцию.

Минимальные инструменты:
- `get_model_rules()` — правила и определения; включает список разрешённых событий.
- `evaluate_scenario(decisions)` — реальная серверная валидация и расчёт.
- `run_stress_test(decisions, event_id)` — отдельный эксперимент по разрешённому событию.
- `get_evidence(result_id, district_id, metric_id)` — получить точные записи происхождения числа из результата текущей сессии.
- `compare_scenarios(a, b, event_id)` — сравнение двух пользовательских вариантов, если функция A/B уже реализована; до этого не объявлять инструмент доступным.

Agentic flow обязателен до завершения первой версии: запрос пользователя → модель запрашивает инструмент → сервер выполняет его → возвращает вывод модели → модель при необходимости запрашивает дополнительные данные → объясняет результат. Реализуй настоящий цикл, не один сгенерированный отчёт и не заранее проигрываемый список шагов.

Для типового запроса с зимним событием должны реально выполняться расчёт обычного сценария и стресс-тест. Порядок/необходимость дополнительного evidence выбирает модель. Не заставляй её тратить вызовы на ненужные шаги ради зрелищности. Ответ без необходимых фактов не считается завершённым аудитом.

Связывай инструменты со снимком пользовательского плана на сервере: модель не может незаметно подменить меры или коэффициенты в аудите. Проверяй совпадение нормализованных decisions с входным снимком; идентификаторы результатов/evidence относятся к этому запуску. Инструменты получают only allowlisted IDs и не могут обратиться к чужому запуску.

После создания схем инструментов выполни небольшой реальный tool-calling smoke test, не только текстовый hello. Если провайдер поддерживает strict schema — используй её, но всё равно проверяй аргументы на сервере. Для nullable district у city нормализуй null до отсутствующего поля. Форматы Responses и Chat Completions не смешивай.

Где возможно, передавай события начала/завершения инструментов по потоку. Если поток в данной среде недоступен, честно покажи загрузку и полученный журнал после выполнения; не генерируй фиктивные промежуточные события. Сохраняй конечное состояние и безопасно обрабатывай разрыв соединения.

Пользователь нажимает «AI-аудит» и выбирает доступное событие. Агент должен получить официальный расчёт и результат эксперимента инструментами, затем объяснить связанные изменения. В журнале показывай фактические tool name, безопасные аргументы, время, статус и возвращённые факты. Не выводи внутренний chain-of-thought и не рисуй фиктивные строки «Testing alternative».

Валидация tool arguments обязательна. Имена функций и event IDs — только allowlist, без eval, доступа к shell или возможности менять датасет. Инструменты не дают агенту самостоятельно сохранить или применить новый план пользователя.

Ограничить выполнение: например максимум 4 model turns, 8 tool calls и timeout около 45 секунд на аудит, с понятным остановленным состоянием. Не вызывать модель после каждого движения мыши. Не делать неограниченные повторные запросы при ошибках. Таймаут/лимиты уточни по фактически используемому SDK.

AI-ответ структурируй как короткое объяснение наблюдаемых изменений, ограничения модели и список evidence IDs. Историю хранить компактно и связывать с актуальным снимком; последующие вопросы должны получать соответствующие данные, а не пересказывать старый отчёт. Где поддерживается, используй schema-based output; не путай соблюдение JSON schema с гарантией истинности текста.

Проверяй evidence IDs по серверному журналу. Неизвестные ссылки не отображать как доказательства. Основные числа и значения до/после рендерятся сервером/интерфейсом из доказательных записей. Модель не должна сочинять числовые последствия, давать медицинские/политические рекомендации или объявлять оптимальный вариант. Не делай вывод «всё безопасно» из отсутствия значений ниже 40.

Ограничь размер входного запроса, число одновременных анализов и повторы. Не запускай API при каждом выборе карточки. Не допускай публичный неограниченный расход ключа. Если внешнее развёртывание открыто без авторизации, документируй ограничения защиты от расходов. Не подключай оплату или новые платные сервисы без отдельного согласия.

Если API недоступен, обязательный расчёт и стресс-тест работают, но панель честно сообщает «AI-анализ недоступен» с причиной и повторным запуском. Технические тестовые mock допустимы в tests, но не в пользовательской демонстрации под видом реального API.

## 8. Тесты и приёмка

Используй существующий test runner; для нового TypeScript-проекта подойдёт Vitest. Начни с тестов чистого ядра, затем API и одного сквозного сценария. Не откладывай тесты до конца.

Проверить:
- Перенесённые данные, сумму весов и долей населения, 5 районов/10 индикаторов/14 мероприятий.
- Baseline и исходный пример по `verification` JSON; не сравнивать округлённые строки.
- Ровно пять решений: 0/4/6 невалидны как пользовательский сценарий.
- Повторы, лимит направления, неизвестные ID, отсутствующий district, лишний district у city.
- Бюджет ровно 100 разрешён; больше 100 запрещён.
- Все три конфликта, включая разрешённые разные районы для двух условных конфликтов.
- City-эффект в каждом районе и однократную оплату.
- Все три синергии с фиксированными бонусами и без масштабирования лагом.
- Отрицательный эффект M11, clip, порог строго <40.
- Порядок решений, отсутствие мутации исходных данных и отсутствие округления внутри вычислений.
- Event none равен официальному результату; повтор winter_demo не накапливает эффект; параметры и версия события неизменны; A/B использует одно событие.
- Невалидный сценарий не получает ни официальный числовой Score, ни экспериментальный результат.
- Устаревшие ответы AI, неизвестные evidence IDs, отсутствие ключа и ошибки API.
- Реальный API smoke test и реальный цикл вызова инструмента при наличии доступа, без публикации секретов.
- Изменение выбора района/индикатора и переходы сцены исходное/расчёт/событие; наличие осмысленной легенды.
- Нажатие evidence действительно открывает нужный расчёт, а не общую справку.
- Повторный вопрос агента использует данные актуального снимка; отменённый или устаревший ответ не подменяет текущий.

Запусти доступные test, typecheck, lint, production build. Для визуальной проверки запусти приложение и проверь основной сценарий в браузере, если инструмент браузера реально доступен. Если нет — прямо укажи, что ручная браузерная проверка остаётся команде; не выдумывай скриншоты и результаты Playwright.

## 9. Порядок реализации — агент входит в основной продукт

Не дели план так, чтобы настоящий агент оказался в необязательных функциях. Один минимальный законченный продукт включает математику, премиальную интерактивную сцену, реальный tool-calling agent, один стресс-тест, проверки и README.

Этап 1: осмотр репозитория и безопасная проверка GitHub/API; данные, контракт, валидатор, движок, первые тесты. Одновременно создай каркас основного экрана с общей визуальной системой. Первый осмысленный checkpoint.
Этап 2: инструментальный агент, зимний эксперимент и evidence; свяжи их с рабочим интерфейсом. Реальный end-to-end сценарий и следующий checkpoint. Не замени этот этап генерацией одного текстового отчёта.
Этап 3: законченная изометрическая сцена, последующие вопросы, понятные состояния и проверка браузером. Полировка не должна сломать работающие данные и AI.
Этап 4: полный набор проверок, README, STATUS, демонстрация, чистый запуск и опубликованный код в командном GitHub.

Только затем — A/B и экспорт. Не делать полный перебор, автоматическую оптимизацию, несколько кризисов, авторизацию, базу данных, PDF, обученную с нуля нейросеть или отдельные приложения.

Ранее упомянутые 4,5 часа не являются новым таймером. Если точный актуальный дедлайн известен из окружения/сообщения — используй его. Если неизвестен, не останавливай реализацию: работай короткими этапами и не обещай срок. В последние 45–60 минут до известного дедлайна только стабилизация, документация и отправка.

Не обещай «успеем всё». После этапа обновляй короткий STATUS.md: реализовано, проверено, команды/результаты, блокеры. Отличай промежуточно работающий расчёт от готового продукта с агентом.

## 10. README и демонстрация

README на русском должен описывать только реализованное:
- Назначение и пользовательский сценарий.
- Источники и синтетический характер данных.
- Архитектуру и точную роль LLM.
- Предпосылки, установку, `.env.example`, запуск и тесты.
- Разделение официальной формулы и дополнительных стресс-допущений.
- Разрешённые инструменты, лимиты агента и поведение без API.
- Трактовку правил направлений и другие ограничения.
- Сценарий проверки для жюри и реально выполненные тесты.
- Вклад участников по фактическим данным команды, не выдуманные коммиты.
- Ссылку на работающий deployment только если он существует.

Демонстрация, примерно 90–120 секунд:
1. Исходные данные, 100 единиц и пять решений.
2. Загрузить пример организатора или показать выбранный пользователем валидный набор; открыть расчёт.
3. Нажать AI-аудит/стресс-тест, показать параметры события до запуска.
4. Показать изменившиеся индикаторы и реальный журнал инструментов; открыть происхождение одного числа.
5. При наличии P2 сравнить два пользовательских набора под одинаковым событием. Не объявлять победителя и не гарантировать благоприятный результат.
6. Показать тесты и запуск по README.

Экспорт, если реализован: «Паспорт симуляции», версия модели, набор решений, исходные/рассчитанные показатели, допущения event, реальные evidence и ограничения. Не использовать оформление официального сертификата или слова об одобрении городских мер.

Сдача: код в выданном командном GitHub-репозитории и отдельная кнопка «Сдать решение» на странице кейса. Наличие локального проекта или git commit не означает завершённую сдачу. Не утверждай, что ты нажал эту кнопку, если не выполнял действие.

## 11. GitHub — сохранение результата обязательно

Организаторы требуют итоговый код в выданном платформой командном репозитории. Промежуточные коммиты — выбранный нами порядок работы, не отдельное правило организаторов. Подключение GitHub к Codex само по себе не является доказательством публикации результатов.

Пользователь разрешает создавать осмысленные коммиты и отправлять изменения ЭТОГО проекта в уже подключённый командный репозиторий доступным штатным способом. Это не разрешение обходить ограничения среды, изменять права, открывать приватный репозиторий, создавать другой remote или автоматически сливать PR в защищённую ветку.

### До изменений
1. Проверь `git status --short --branch`, текущую ветку, историю, имеющиеся remotes и инструкции репозитория. Удали секреты из отображаемых URL перед выводом; не печатай токены, даже если они встроены в URL remote.
2. Работай внутри выданного репозитория, без вложенной `.git`, нового GitHub-репозитория и подмены origin. Если адрес выданного репозитория неизвестен, сначала прочитай доступные инструкции/контекст среды, затем спроси только недостающее. Не считай случайный remote подтверждённым адресом команды.
3. Уважай изменения других участников. Не выполняй `reset --hard`, `clean -fd`, force-push, удаление веток, переписывание истории, автоматический stash или изменение глобального Git config.
4. В Codex Cloud используй созданную средой рабочую ветку. Локально используй принятую рабочую ветку проекта. Не предполагая, что основная ветка обязательно называется main, выясни её по репозиторию.

### После законченных этапов
- Обнови STATUS.md реальными результатами. Не указывай выдуманное время, результаты тестов или готовность агента.
- Проверь изменения, `.gitignore` и staged diff. Не добавляй `.env`, `.env.local`, другие секретные env-файлы, токены, `node_modules`, `.next` или логи запросов с ключами. `.env.example` содержит только пустые/безопасные значения. Исходные документы и JSON можно включить в репозиторий для воспроизводимости.
- Добавь явно относящиеся к этапу файлы. Не делай слепой `git add .` поверх чужих или секретных файлов.
- Создай осмысленный commit с существующей настроенной Git-идентичностью. Примеры названий — `feat: add validated simulation engine`, `feat: connect audit agent and winter test`, `feat: finish interactive city scene`, `docs: add verified demo and setup`. Не создавай пустые коммиты ради количества.
- Если среда разрешает прямую отправку, выполни обычный `git push` в соответствующую рабочую ветку существующего remote. Соблюдай требуемые средой approvals. Не запускай бесконечные попытки при запрете сети/авторизации.
- После отправки проверь remote: нужный commit действительно присутствует в удалённой ветке. Сам локальный commit не доказывает публикацию. Используй безопасную проверку remote ref/истории; свежие чужие commits не перезаписывай.
- Если Codex Cloud использует публикацию через PR вместо прямого push, подготовь изменения для Create PR / штатного механизма платформы. Создай/обнови PR, только если действие действительно доступно. При необходимости ручной кнопки прямо скажи пользователю, что именно нужно нажать. Не заявляй «отправлено», пока не получил подтверждение.
- Если push/PR блокирован сетью, разрешениями или недостающей Git-идентичностью, сохрани код и доступный локальный checkpoint; сообщи точную проблему без секретов. Не придумывай имя/email и не предлагай вставить токен в чат.

### Перед сдачей
- Ещё раз запусти проверки и отправь последнюю рабочую версию. Подтверди репозиторий, ветку и hash опубликованного commit; ссылку на PR — только существующую.
- Отдельно укажи состояние объединения: находится ли код только в рабочей ветке/PR или уже в основной/указанной для проверки ветке. Из исходных файлов не следует, что платформа проверяет конкретное название ветки. Не выдавай незамерженный PR за обновлённую основную ветку.
- Не обходи branch protection. Когда требуется ручное объединение, дай точное оставшееся действие. Слияние — после просмотра человеком, а не безусловно.
- Не делай вид, будто GitHub Pages с одной статикой запустит серверный API. Развёртывание и хранение исходников в GitHub — разные задачи. Если deployment не выполнен, README должен позволять локальный запуск.
- В итоговом сообщении отдельно: что реализовано, какие проверки реально прошли, как запустить, API статус, GitHub статус, оставшиеся ручные действия. Не называй отправку в репозиторий нажатием кнопки «Сдать решение».

Вклад команды: каждый участник должен реально участвовать. Можно фиксировать фактическое тестирование, отчёты об ошибках, документацию и демонстрацию; не выдумывать авторство кода, соавторов commits или выполненные задачи. Создай секцию вклада с фактами, которые предоставила команда; неизвестные имена не сочиняй.

## 12. Начни сейчас

Коротко сообщи состояние репозитория и ветки, выбранный стек/совместимость, статус API smoke test без секретов и следующий этап. Не выдавай подключённый GitHub за уже опубликованный результат. Затем сразу реализуй первый проверяемый этап и продолжай к законченной первой версии с настоящим агентом, объёмной сценой и GitHub-checkpoints. Не останавливайся на плане. Не останавливайся после одного плана или каждого обычного действия ради подтверждения. Продолжай последовательно, сохраняя checkpoints. Если задачу приходится завершить до готовности, оставь STATUS.md и точный следующий шаг; не изображай незавершённое приложение готовым.
